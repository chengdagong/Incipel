Incipel agent architecture 变更说明

本文记录本次将 agent runtime 从 Supabase Edge Function 迁移到 Mastra application + Hono server adapter 的设计背景、代码边界、运行流程、本地开发变化和后续部署影响。 移动端继续消费 AG-UI SSE 事件，Supabase 继续负责 Auth、Postgres 和 Storage。

状态：已实现并通过验证 运行时：Mastra application 协议：AG-UI over SSE 数据层：Supabase
摘要 为什么改 前后对比 运行流程 代码边界 本地开发 部署影响 验证记录 后续事项

1. 摘要

这次变更只移动 agent runtime 的承载方式，不改移动端协议，不改核心数据模型， 也不把产品语义交给第三方 framework。

Changed

agent runtime 改为 Node server

packages/agent/src/mastra-app.ts 注册 Mastra application 和 agents；AG-UI HTTP routes 直接注册到外层 Hono app，再由 @mastra/hono 初始化。

Kept

AG-UI 协议保持不变

移动端仍通过 /run 接收 AG-UI SSE 事件： 文本流、tool call 事件、STATE_SNAPSHOT 和 STATE_DELTA 的行为继续由 Incipel 代码控制。

Moved

Supabase 回到数据层角色

Supabase 继续负责 Auth、Postgres、Storage 和本地开发数据库； supabase/functions/agent 仅保留历史入口，不再作为新的 agent runtime 部署目标。

2. 为什么改

Incipel 的 agent 不是普通 HTTP handler。它需要长程对话、streaming、 结构化 tool use，以及未来的 skill、hook、subagent 等机制。

Supabase Edge Function 承载 agent

旧方案
适合轻量 HTTP 入口

用来接收请求和返回短响应很直接，但长轮 streaming agent 会暴露运行时限制。

Deno 依赖图较难维护

Node 生态 agent framework、测试工具和 provider SDK 的组合需要额外适配。

本地多 worktree 不够顺手

多个开发 worktree 共用 Supabase stack 时，agent 热重载和端口隔离成本较高。

Mastra application server

新方案
agent 行为放在 agent 层

Mastra application 负责注册 Agent、tool 注册、streaming chunk 和模型调用；AG-UI HTTP routes 仍由 Incipel 的 Hono handlers 承载。

协议边界仍由项目控制

外层 Hono routes 继续输出 AG-UI SSE，不让 Mastra 接管移动端协议。

为后续机制保留空间

skill、hook、subagent 以后可以从 Mastra 层扩展，避免把这些能力塞进 Edge Function。

3. 前后架构对比

旧方案把 HTTP 入口、agent 编排和模型 provider 都放在 Supabase Function 中。 新方案把 agent runtime 独立为 Node server，Supabase 专注保存用户、会话和剧本数据。

Before

Edge Function runtime
RN / Expo mobile app

请求 /functions/v1/agent，消费 AG-UI SSE。

↓ HTTPS + JWT
Supabase Edge Function

承载 Hono app、authentication、run orchestration 和 model runtime。

↓ direct provider call
AI SDK + OpenRouter provider

项目代码直接处理 provider 事件并转换为内部 stream chunk。

↕
Supabase data plane

Auth、Postgres、Storage，同时也承载 agent runtime。

After

Mastra application runtime
RN / Expo mobile app

请求 EXPO_PUBLIC_AGENT_URL，继续消费 AG-UI SSE。

↓ HTTPS + JWT
Mastra application + Hono adapter

Incipel 先把 /run、/logline 和 /health 直接注册到 Hono app，@mastra/hono 再初始化同一个 app；@hono/node-server 只负责监听 HTTP。

↓ Mastra Agent.stream
Mastra + OpenRouter

Mastra agent 处理 model streaming、tool schema 和 tool call 生命周期。

↕ service role
Supabase data plane

Auth、Postgres、Storage；不再部署新的 agent runtime。

4. 运行流程

外层 run orchestration 仍由 Incipel 实现。Mastra application 接管 agent registry、 模型调用的 framework 部分，AG-UI routes、事件生成、数据库事务和产品状态更新仍在项目代码内完成。

/run：对话回合

1

外层 Hono route 校验客户端 JWT，并确认用户可以访问目标 session。

2

读取当前 Screenplay state、最近 messages 和本轮用户输入。

3

根据当前 state 生成 prompt 和 tool schema，再调用 Mastra Agent.stream。

4

把 Mastra chunks 转成项目内部 StreamChunk：文本、tool call start、tool call payload。

5

run orchestration 应用 tool call，发出 AG-UI 文本事件和 STATE_DELTA。

6

回合结束后保存 assistant message、最新 document state 和必要的 document version。

/logline：欢迎页灵感生成

1

客户端请求 logline 生成，不写入数据库。

2

model provider 使用 Mastra agent 走一次短生成，maxSteps 设为 1。

3

返回修剪后的 logline 文本，由客户端填入输入框。

4

用户点“开始创作”后，真正的 session 和 document 再由后续流程创建。

关键不变量： AG-UI 事件、Screenplay mutation contract、authentication、SupabaseStore 仍属于 Incipel 的核心边界。Mastra 是 agent framework，不是产品协议的拥有者。

5. 代码边界

本次变更把“模型 framework 适配”和“产品运行编排”分开。下面这些文件是理解新架构的入口。

packages/agent/src/index.ts Node server entrypoint。读取 HOST、AGENT_PORT 或 PORT，创建 Hono app，交给 MastraServer 初始化后再启动 HTTP server。
packages/agent/src/mastra-app.ts Mastra application registry。注册 screenwriter、logline agents，并配置 Mastra framework storage。
packages/agent/src/routes.ts Hono route handlers。负责 /run、/logline、/health、authentication、SSE response 和 store 注入。
packages/agent/src/app.ts 测试用 Hono wrapper。让既有 app.request() 测试继续覆盖同一组 route handlers。
packages/agent/src/model/mastra.ts Mastra provider adapter。从 Mastra application registry 获取已注册 agents，再把 Incipel prompt、tool definitions 和 model config 映射为 Agent.stream() 与 createTool()。
packages/agent/src/model/provider.ts model provider selection。MODEL_PROVIDER=stub 用测试 provider，openrouter 走 Mastra provider。
packages/agent/src/model/config.ts 模型配置读取。保留 provider options，但不再直接依赖旧 AI SDK provider。
tools/incipel-dev/cli.mjs 本地开发 orchestration。为每个 worktree 计算稳定 agent port，写入 env，并后台启动 pnpm --filter @incipel/agent dev。
scripts/dev-android.sh · scripts/dev-ios.sh 移动端开发脚本。Android 会同时 reverse Supabase API port、Metro port 和 agent server port。
supabase/functions/agent 历史入口。保留文件用于说明迁移结果，运行时会明确报错；不要再把它作为新的 agent 部署目标。

依赖变化

类型 包 说明
新增 @mastra/core 提供 Mastra application、Agent、tool registration 和 streaming runtime。
新增 @mastra/hono 提供 Hono server adapter，用 MastraServer 初始化 Hono app 并注册 Mastra routes。
新增 @hono/node-server 在 Node 环境监听 HTTP；当前使用 1.19.14 以满足 @mastra/hono 的 peer dependency。
保留 hono 承载 AG-UI SSE routes，同时作为 Mastra Hono adapter 的 app 容器。
保留 ai 继续使用 v6；Mastra 也基于 AI SDK 运行模型调用。
移除 @openrouter/ai-sdk-provider OpenRouter 接入改由 Mastra model configuration 承担。
保留 zod 3.x 项目现有代码仍使用 Zod 3 API；Mastra 支持该版本范围，因此暂不改到 Zod 4。

6. 本地开发变化

新方案的本地开发重点是：日常 dev agent server 使用固定端口 4111， E2E runner 才使用 worktree 相关端口。移动端通过 EXPO_PUBLIC_AGENT_URL 指向对应 server。

常规开发

pnpm dx up

tools/incipel-dev 会同步 apps/mobile/.env 和 supabase/.env，然后启动 agent dev server。agent server 的健康检查地址为 http://127.0.0.1:4111/health。

单独启动 agent

pnpm --filter @incipel/agent dev

server 从环境变量读取 SUPABASE_URL、SUPABASE_SERVICE_ROLE_KEY、 MODEL_PROVIDER、OPENROUTER_API_KEY 和 AGENT_PORT。

变量 写入位置 用途
EXPO_PUBLIC_AGENT_URL apps/mobile/.env 移动端访问 Mastra application agent server 的 base URL。
AGENT_PORT supabase/.env 日常 dev agent server 监听端口，固定为 4111；E2E runner 使用 worktree 相关测试端口。
SUPABASE_URL supabase/.env agent server 访问本地或远端 Supabase API。
SUPABASE_SERVICE_ROLE_KEY supabase/.env 服务端保存 messages、documents 和 document_versions。

Android 变化： 设备或 emulator 需要同时访问 Metro、Supabase API 和 agent server。 因此 scripts/dev-android.sh 会根据 apps/mobile/.env 中的 agent URL 追加对应的 adb reverse。

7. 部署影响

生产环境以后需要一个 Node hosting target 来运行 agent server。Supabase Function 不再是 agent 的生产部署目标。

需要新增的部署职责

  • 选择 Node hosting target，例如 Cloud Run、Fly.io、Railway 或自有容器平台。
  • 为 agent server 配置 secrets：Supabase service role key、OpenRouter API key、JWT 参数。
  • 为 /health 配置健康检查。
  • 把移动端生产环境的 EXPO_PUBLIC_AGENT_URL 指向新的 HTTPS endpoint。

继续不变的部署职责

  • Supabase migrations 继续管理 Postgres schema。
  • Supabase Auth 继续签发客户端 JWT。
  • 客户端仍按 AG-UI SSE 事件渲染文本、inline cards 和文档状态。
  • RLS 与服务端访问边界继续由 Supabase 配置和 agent store 共同约束。

推荐原则： 先选择最容易观察日志、配置 secrets、支持 streaming response 的 Node hosting target。 不要同时维护 Edge 与 Node 两套生产 agent runtime，否则会增加部署、监控和文档维护成本。

9. 后续事项

本次变更已经完成开发和本地验证。上线前还需要把运行环境和后续 agent 能力设计补齐。

Deploy

选择生产 Node hosting target

比较 streaming response、日志、secret 管理、region、成本和回滚方式，再写入新的部署 ADR。

Observe

补充 runtime 观测

为 /run 增加结构化日志、provider latency、tool call count、error code 和 session-scoped trace id。

Extend

设计 skill / hook / subagent

以 Mastra application 为扩展点，但保持 AG-UI 事件和 Screenplay mutation contract 由 Incipel 负责。
